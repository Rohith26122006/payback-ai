# Limitations and Future Work

## Data and simulation limitations

- **Synthetic data only.** Every distribution, correlation, and "ground truth" recovery
  outcome in this system was generated by `data/generate_synthetic_data.py`'s assumptions,
  not observed from real payment behavior. Model metrics (recovery model ROC-AUC 0.735,
  classifier 100% match to ground truth) reflect fit to that synthetic generator, not
  real-world predictive power.
- **Single-shot dataset.** Each transaction has exactly one recorded failure event, not a
  multi-round history of retries over real elapsed time. "Average recovery time" is
  therefore a proxy (`time_since_failure_minutes` at the one recorded event), not a measured
  time-to-resolution across multiple real attempts.
- **Illustrative probabilities.** The simulator's customer-response rate (55%) and human
  approval rate (65%) for reminders and escalations are stated assumptions
  (`core/simulator.py`), not measured rates.
- **Illustrative costs.** `evaluation/costs.py`'s per-retry/message/review costs are
  assumptions for making cost-per-recovery legible, not Razorpay's real internal costs.

## A real bug found and fixed during development (documented, not hidden)

The What-If Simulator (Stage 13) originally reused the exact same policy-evaluation code
path as the live pipeline, which reads real `action_events` history to enforce cooldowns,
retry counts, and duplicate-action prevention. Because the real pipeline's history was all
timestamped within moments of each other, **every** what-if scenario tripped the
duplicate-action and cooldown rules regardless of the policy being tested, flattening
recovery rate to 0% no matter what the sliders were set to.

This was caught by actually running the tool against real data before shipping it (not by
the automated test suite, which had passed). The fix: `make_decision()` gained an
`ignore_history: bool` parameter (`core/decision_engine.py`) — when `True`, policy
evaluation treats the transaction as if it had no prior history, which is what "what if we'd
used this policy" should mean. After the fix, the default-policy what-if result exactly
reproduces the real persisted run's recovery rate (29.58%), which is how it was validated as
actually fixed rather than just no-longer-crashing.

## Architectural simplifications

- No multi-round retry simulation over real elapsed time — everything is one decision per
  transaction, evaluated once.
- The recovery model is a single logistic regression; the spec allows for gradient boosting
  if logistic regression proves insufficient, but on this dataset it wasn't necessary.
- The LLM layer's real provider (`llm/claude_provider.py`) is implemented but never
  exercised against the real Claude API in this project (no key was used) - only the mock
  provider's behavior and the fallback logic are verified end-to-end.
- `review_queue` resolution (approve/reject) doesn't feed back into the recovery model or
  decision table - a human's decision is recorded and audited, but doesn't currently retrain
  or adjust future automated decisions.

## Future work

- Multi-round simulation: model a transaction's full retry history over simulated elapsed
  time, rather than one decision per transaction.
- Feed human review outcomes (approve/reject) back as a signal the recovery model or
  decision table could eventually learn from.
- Try a gradient-boosted model alongside logistic regression and compare, now that the
  leakage-safe feature pipeline (`core/recovery_model.py`) already exists.
- A/B-style evaluation across multiple random seeds to report confidence intervals on the
  baseline-vs-PayBack-AI comparison, rather than a single seed=42 run.
- Real Claude API integration testing (currently implemented but unexercised without a key).
