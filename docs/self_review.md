# Final Review — Razorpay Hiring Panel Perspective

This is Stage 17, the last stage. Everything below is based on an actual clean-room rebuild
(fresh clone, fresh venv, `--reset` database, zero cached state) run during this review, not
on memory of earlier stages.

## What was verified in this review

- **Full clean-room reproducibility**: cloned the repo fresh, created a new venv, ran every
  pipeline command from scratch. Every number matched the previously-documented results
  exactly (recovery rates, revenue, costs, latency) — the seeded pipeline is genuinely
  deterministic, not just claimed to be.
- **167/167 tests passing** in the clean-room copy, independent of any earlier run.
- **Line-by-line read of `core/policy_engine.py` and `core/decision_engine.py`** (the two
  safety-critical files) as a PR reviewer would. Findings: rule ordering is deliberate and
  documented, `stop_after_success` correctly short-circuits everything below it, the
  `ignore_history` parameter (added to fix the Stage 13 bug) is scoped narrowly and doesn't
  leak into the normal decision path. No correctness issues found on this pass.
- **Grep for fake placeholders/TODOs** across the project's own code (excluding
  dependencies): none found. The one `placeholders` match is a legitimate SQL parameter
  string in `data/seed_database.py`, not a stub.
- **Grep for SIMULATED/synthetic labeling discipline**: consistently present at every
  outcome-producing point (simulator, baseline, dashboard, evaluation reports).

## What a hiring panel would likely praise

- **The policy engine actually is authoritative**, not just described that way. It's
  demonstrated end-to-end: a `suspected_risk` transaction proposing `delayed_retry` gets
  forced to `human_escalation`, tested in isolation (`tests/test_policy_engine.py`) and
  end-to-end (`tests/test_decision_engine.py`, the dashboard, the API).
- **The evaluation is honest**, not a marketing table. PayBack AI loses on raw recovery rate
  (29.58% vs 34.58%) and cost-per-recovery (₹18.08 vs ₹3.52) against its own baseline, and
  the README leads with that rather than burying it. It wins decisively on unnecessary
  retries (20.42% vs 45.75%), and that's presented as the actual point of the system, not
  spun as a clean sweep.
- **A real bug was found and documented, not hidden.** The what-if simulator's original bug
  (contaminated by real action history) is written up plainly in `docs/limitations.md` with
  the actual symptom (recovery rate stuck at 0%), how it was caught (running it, not just
  passing tests), and the fix (`ignore_history` parameter). That's a stronger signal than a
  project with no visible mistakes.
- **Test coverage traces directly to the spec.** `tests/test_reliability.py` maps 1:1 to the
  13 required reliability scenarios by name, and 3 of them (invalid model output edge case,
  DB CHECK constraints, API 422s) were genuine gaps found and filled in Stage 15, not
  padding.
- **The safety design is defense-in-depth**, not a single check: policy engine overrides
  unsafe actions, the LLM content filter independently rejects unsafe *language* even when
  the action itself was already safe, and DB-level CHECK constraints catch malformed data
  that somehow bypassed both.

## What a hiring panel would likely push back on

- **The recovery model is unvalidated against anything real.** ROC-AUC 0.735 is measured
  against a synthetic ground truth generated by the same kind of logic the model is trying
  to learn — a panel would (correctly) ask "what does this number mean outside this
  simulation," and the honest answer, stated in `docs/limitations.md`, is "not much yet."
- **Single-shot dataset is a real limitation, not just a caveat.** Every transaction gets
  exactly one decision; there's no simulated multi-round retry history over actual elapsed
  time. "Average recovery time" is acknowledged as a proxy, not a measured quantity — a
  panel would want to see this addressed before trusting the number in a real pitch.
- **The `ignore_history` fix, while correct, is a narrow patch for a specific symptom.** A
  more thorough fix might separate "policy evaluation" more cleanly from "history lookup" as
  distinct injectable dependencies from the start, rather than adding a boolean flag after
  the fact. The current fix works and is tested, but a stricter reviewer might ask for a
  cleaner abstraction if this were headed to production.
- **Illustrative constants (cost assumptions, simulator response/approval rates) are
  reasonable but arbitrary.** They're clearly labeled as assumptions, which is the right
  call for a prototype, but a panel evaluating this for a real revenue-recovery product would
  want these calibrated from actual data before the cost-per-recovery numbers mean anything
  operationally.
- **The Claude provider is implemented but never exercised against a real API.** It's
  reasonable given no key was available, but it means the "optional real LLM" path is
  untested code, not just an unused feature.

## Bottom line

This is a genuinely safety-first prototype where the interesting engineering is in the
policy layer, not the ML — which matches what the brief actually asked for (an AI revenue-
recovery system that doesn't do anything reckless) rather than chasing the highest possible
recovery-rate number. The honest evaluation, the documented bug-and-fix, and the 1:1
spec-to-test traceability are the strongest parts of this submission. The weakest parts are
exactly what you'd expect from an unvalidated synthetic prototype: no real-world signal on
the ML model, and cost/probability assumptions that would need real data before they mean
anything operationally. Both are named plainly rather than glossed over.
