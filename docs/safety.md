# Safety and Threat Model

This document maps every "must never" constraint from the project spec to the code that
actually enforces it, so it can be checked rather than taken on faith.

## Core principle: the Policy Engine is authoritative

Neither the ML recovery model nor the LLM message generator can make an unsafe action
happen. The decision engine only ever *proposes*; `core/policy_engine.py` has the final
word and can only restrict or replace a proposal — never invent a riskier one.

## The 9 safeguards (`core/policy_engine.py`, defaults from `PolicyConfig`)

| # | Safeguard | Default | Enforced by |
|---|---|---|---|
| 1 | Deterministic fallback if model/LLM output is invalid | always on | `deterministic_fallback_action()` - ignores the proposal entirely, uses category + attempt count only |
| 2 | Stop all pending actions after success | always on | `stop_after_success` rule - highest priority, short-circuits every other rule |
| 3 | Prevent duplicate action execution | always on | `prevent_duplicate_execution` rule |
| 4 | No automatic retry for suspected-risk transactions | always on | `no_auto_retry_suspected_risk` rule |
| 5 | Escalate unknown failure types | always on | `escalate_unknown_failure` rule |
| 6 | Maximum automatic retries | 2 | `max_auto_retries` rule |
| 7 | Minimum retry cooldown | 30 minutes | `retry_cooldown` rule |
| 8 | Maximum customer messages | 1 per 24h | `max_messages_per_24h` rule |
| 9 | Escalate uncertain or high-value transactions | confidence < 0.5 OR amount > INR 50,000 | `escalate_uncertain_or_high_value` rule |

Every rule's outcome - fired or not - is recorded in `safety_checks` on every decision, so
the full trace is auditable even when nothing was overridden (see any transaction detail in
the dashboard, or `recovery_decisions.safety_checks` directly).

## LLM constraints (`llm/message_generator.py`)

The spec's "The LLM must not..." list, operationalized in code:

| Constraint | Enforcement |
|---|---|
| Invent payment status / claim success | Content filter rejects phrases like "payment was successful", "confirmed successful" (`FORBIDDEN_SUBSTRINGS`) |
| Invent discounts or policies | Content filter rejects "discount", "refund", "% off", "guarantee", "cashback", "free " |
| Reveal sensitive data | System prompt instructs the LLM never to reveal internal risk scores, confidence, or identifiers; the LLM is never given raw internal IDs in its prompt to begin with - only `action` and a rephrased `reason` |
| Make unrestricted financial decisions | The LLM never sees or influences `action`, `confidence`, or `requires_human_review` - those are set by the decision engine and policy engine before the LLM is ever called, and passed through unchanged |
| Override policy rules | Structurally impossible - the LLM only drafts `customer_message` text, called *after* the policy engine has already finalized the action |
| Send real messages | Nothing in this codebase sends anything - `customer_message` is a string returned to the caller, nothing more |

**On any failure** - provider exception, timeout (enforced via a hard wall-clock deadline,
`_call_with_timeout`), invalid JSON, a Pydantic validation error, or forbidden content - the
LLM's output is discarded entirely and a deterministic, safe template message is used
instead (`deterministic_fallback_message`). The application runs fully with **zero API key**
(`MockLLMProvider` is the default) - this is tested directly in `tests/test_llm.py`.

## Audit trail

`core/audit_logger.py` is append-only by construction - the module provides no update or
delete function. Every simulated action, decision recomputation, message generation, and
review resolution writes an entry. Nothing in the pipeline can silently erase what happened.

## Data safety

- All payment data is synthetic, generated by `data/generate_synthetic_data.py` with no
  real names, card numbers, bank details, UPI IDs, phone numbers, or emails.
- `customer_id_hash` is a SHA-256 hash of a synthetic index, not derived from any real
  identifier.
- No real payment gateway (Razorpay or otherwise) is called anywhere in this codebase
  (verified by grep in Stage 15 - see `PROJECT_STATE.md`).
- No hardcoded secrets anywhere; `ANTHROPIC_API_KEY` is read only from the environment and
  the app runs fully without it.
- Every simulated outcome is labeled "SIMULATED" in logs, dashboard badges, and evaluation
  reports - never presented as if it were real.

## Known safety-relevant limitations

- The policy engine's history-aware rules (cooldown, retry count, message limit, duplicate
  detection) read real `action_events` - this is correct for the live pipeline, but required
  a dedicated `ignore_history` code path for the what-if simulator (Stage 13) so hypothetical
  policy exploration isn't contaminated by the real run's timestamps. See
  `docs/limitations.md` for the full story, including the bug this caught.
- Cost assumptions and simulation probabilities (customer response rate, human approval
  rate) are illustrative assumptions, clearly labeled as such in `evaluation/costs.py` and
  `core/simulator.py` - not measured real-world rates.
