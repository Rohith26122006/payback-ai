# Evaluation Methodology and Results

**All numbers below are SIMULATED outcomes computed on SYNTHETIC data (seed=42, 1200
transactions). They are not representative of real-world Razorpay performance and should
not be treated as validated real-world figures.**

## Methodology

Both systems run on the exact same 1200 synthetic failed-payment records:

- **Baseline** (`core/baseline.py`): retry once after a fixed delay, then one generic
  reminder, then stop after 2 attempts. Category-blind by design — it doesn't look at
  `failure_category`, risk signals, or anything else. This is intentional: a baseline
  quietly made smarter than "fixed retry" would make the comparison meaningless.
- **PayBack AI**: classifier -> recovery-probability model -> decision table -> policy
  engine (authoritative) -> simulator.

For actions that constitute an actual attempt, the ground-truth `payments.recovery_outcome`
field (generated alongside the synthetic data) determines whether that attempt succeeds —
this represents "was this transaction recoverable at all," independent of strategy, and is
only realized if an action is actually taken. See `core/baseline.py` and `core/simulator.py`
docstrings for the full statement of this assumption.

## Metric Definitions (the non-obvious ones)

- **False-Positive Decision Rate**: share of transactions where the system chose
  `stop_recovery` but the transaction was actually recoverable (ground truth) — i.e. gave up
  on something that could have been recovered. Only measurable because this is synthetic
  data with a known answer.
- **Policy Violations Caught**: number of decisions where the policy engine had to override
  the decision engine's initial proposal. The baseline's count is always **0** by design — it
  never goes through the policy engine at all, which is a real structural difference, not a
  data quirk.
- **Decision Latency**: measured by actually timing the decision function, not estimated.
  Baseline's decision (`decide_baseline_action`) is a pure O(1) lookup with zero database
  access; PayBack AI's (`make_decision`) performs several real SQL reads (classifier output,
  recovery probability, action history). These numbers are **intentionally not
  apples-to-apples** — the asymmetry itself is part of what the comparison shows.

## Cost Assumptions

Configurable in `evaluation/costs.py`, clearly labeled as illustrative:

| Assumption | Value (INR) |
|---|---|
| Cost per automated retry | 2.0 |
| Cost per customer message | 0.5 |
| Cost per human review | 50.0 |

These are **not** Razorpay's real internal costs.

## Results

| Metric | Baseline (fixed-retry) | PayBack AI |
|---|---|---|
| Recovery Rate | 34.58% | 29.58% |
| Recovered Revenue (INR) | 2,084,060.68 | 1,834,544.83 |
| Average Recovery Time (min) | 723.2 | 720.3 |
| Unnecessary Retry Rate | 45.75% | 20.42% |
| Messages per Recovered Payment | 0.749 | 0.594 |
| Cost per Recovery (INR) | 3.52 | 18.08 |
| Human Escalation Rate | 0.00% | 9.17% |
| False-Positive Decision Rate | 4.83% | 6.50% |
| Policy Violations Caught | 0 | 4 |
| Decision Latency (avg ms) | 0.0002 | 0.0676 |

*(Regenerate anytime with `python -m evaluation.evaluate`, which also writes
`evaluation/results.json`.)*

## Reading this honestly

This is **not a one-sided win for PayBack AI**, and the report is written to make that
visible rather than hide it:

- PayBack AI **more than halves** the unnecessary-retry rate (45.75% -> 20.42%) — this is
  the headline win: far fewer wasted automated attempts and fewer annoyed customers.
- PayBack AI's **raw recovery rate is lower** (29.58% vs 34.58%) and its **cost per recovery
  is over 5x higher** (INR 18.08 vs INR 3.52) — both driven by the same cause: PayBack AI
  stops 319 transactions outright and escalates 110 to a simulated human reviewer (who
  sometimes rejects, at a real assumed cost), where the baseline blindly keeps trying
  everything.
- The trade-off is real: **fewer wasted, riskier actions and human oversight on risky/
  high-value cases, in exchange for some raw recovery percentage and per-recovery cost.**
  Whether that trade-off is worth it depends on what a merchant actually values — this
  report gives the numbers to decide, not a verdict.

## Limitations of this evaluation

- Single-shot dataset: each transaction has exactly one synthetic failure event, not a
  multi-round history. "Average recovery time" is a proxy (`time_since_failure_minutes` at
  the point of the one recorded event), not a measured elapsed-time-to-resolution.
- Synthetic recovery probabilities are generated by the same process used to train the
  recovery model, so the model's ROC-AUC (0.735, see `models/recovery_model_metrics.json`)
  reflects fit to that synthetic process, not real-world predictive power.
- See `docs/limitations.md` for the full list.
